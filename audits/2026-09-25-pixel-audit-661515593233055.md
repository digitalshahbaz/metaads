## Problems, by priority

### P1: one pixel is used by 6 websites
Pages sending events to 661515593233055:
- digitalshahbaz.in (your funnel)
- **mex.academy**
- **digimarkmedia.in**: a burst of about 370 events on 20 Sep, 20:00–23:00 PT, almost all server-side
- link.digitalshahbaz.in
- **aiadskill.com**
- **apmp.lovable.app**

Leads, checkouts and purchases from other businesses train the ₹999 campaigns and make the reported purchase count unreliable.

**Fix:**
1. Keep this pixel for digitalshahbaz.in only.
2. Give each other site its own dataset.
3. In Events Manager, go to Settings → **Traffic permissions** and switch to an **allow list** containing digitalshahbaz.in and link.digitalshahbaz.in only.

### P2: check that purchases are deduplicated
Every purchase arrives from both the browser and the server. If the two copies don't share the same `event_id`, Meta counts them twice.

That fits what we've seen before: 26 purchases in Meta against 1 real sale on 18 Aug, and 31 purchases in Meta over the last 7 days.

**Fix:**
1. In Events Manager, open Purchase → **Event deduplication**. It should say "deduplicated" with overlap close to 100%.
2. Make the browser event and the CAPI event send the same `event_id`, using the order or transaction ID.

### P3: two pixels on one funnel
"Ai Meta Ads Program" (1366054208795793) receives the same events. That doesn't break anything by itself, but it splits learning if any ads optimise to it, and it doubles setup mistakes.

**Fix:** pick one pixel (661515593233055, which the ads use). Remove the other from the funnel pages and from the GHL/Kairoas integration.

### P4: Lead event has no email or phone (EMQ 6.1)
The opt-in form collects name, email and phone, but none of it reaches Meta.

**Fix:** send the Lead event through GHL's CAPI or Conversions integration with `em`, `ph`, `fn`, `ln` and `external_id` (the contact ID). Expected EMQ: about 8.5–9.

### P5: AddPaymentInfo fires alongside InitiateCheckout
Both events fire from the same trigger with identical counts, and AddPaymentInfo carries no user data.

**Fix:** fire AddPaymentInfo only when the Razorpay window opens or payment starts, with the same user data as InitiateCheckout. Or remove it.

### P6: ViewContent almost never fires
Only about 4 ViewContent events were received this week.

**Fix:** fire ViewContent on amab-3-page load (or after 50% scroll) with `content_name: "AI Meta Ads Bundle"`, `content_ids: ["AMAB999"]`, `value: 999`, `currency: "INR"`. This gives Meta a middle-of-funnel signal between page view and checkout.

### P7: external_id is weak before checkout
- external_id coverage: PageView 7%, InitiateCheckout 23%, Purchase 90%.

**Fix:**
1. Set a first-party visitor ID in a cookie on the first visit and send it as `external_id` on every event.
2. After opt-in, send the GHL contact ID as `external_id`.

### P8: Purchase parameters
**Fix:**
- Send the actual charged amount (including bumps and upsells) as `value` with `currency: "INR"`.
- Include `content_ids`, `content_type: "product"` and `order_id` (also used as `event_id`).
- Send a CAPI Purchase only on payment success from Razorpay/Kairoas, never on the thank-you page load alone.
- Cover the 10% of purchases that arrive without user data.

### P9: use the offline dataset
"DS Offline 1" (1301659675164580) has never received any data.

**Fix:** upload real paid orders from Kairoas/GHL daily (or connect them through the CRM integration). This gives Meta the true sales count and lets you compare Meta's numbers with real sales.
